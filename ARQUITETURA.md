### Autenticação, sessão e segurança atual

- Login de banco via `usuarios.senha` e `password_verify`; cadastro usa `password_hash(PASSWORD_DEFAULT)`. Para hashes bcrypt, a verificação Node com bcrypt deve ser compatível, mas é necessário inventariar algoritmos/comprimentos de hashes sem expor hashes e adicionar testes de verificação/rehash.
- Sessão server-side do PHP com `session_start()` e cookies; `config.php` tenta ativar `httponly`, `strict_mode` e `SameSite=Strict`, com `secure=0`. Há páginas que iniciam a sessão antes de incluir `config.php`, então a configuração pode chegar tarde.
- Dados correntes: `usuario_id`, `usuario_nome`, `usuario_login`, `is_admin`, token CSRF. `tipo_usuario` é lido numa tela admin mas não é definido no login mostrado.
- CSRF token é criado em páginas e verificado no fórum/admin de formas diferentes; question admin verifica o token sem verificar a sessão/valor ausente de modo uniforme. Fórum tem rate-limit comentado; admin tem rate limit em sessão.
- `verificarAdmin` volta ao banco para papel/conta ativa. Planejar checagem de conta banida e papel em rotas API, logout/revogação, CORS same-origin e CSRF para cookies.
- Durante coexistência PHP/Node, o cookie/sessão padrão PHP não é automaticamente compreensível pelo Node. A proposta de sessão nova exige migração coordenada/ponte temporária; não afirmar interoperabilidade até testar.

### Backend e schema sem migração de banco

Cada módulo segue `routes -> service -> repository`. Routes fazem parse de params/body/cookie com schemas Zod e escolhem status/headers; services aplicam regras; repositories contêm queries parametrizadas Drizzle. Acesso a banco único por plugin/injeção, transações no fechamento de teste. Não compartilhar objetos DB com React.

Drizzle é preferido ao Prisma nesta proposta por explicitar queries e mapear incrementalmente tabelas legadas divergentes. O modelo deve ser gerado/ajustado com base no schema **real** introspectado, não em migrations conflitantes do repositório. Desabilitar criação automática/`push`; sem `drizzle-kit push`, sem DDL, sem renomear/adicionar colunas. Guardar snapshot do schema usado por build/testes, com secrets removidos.

### Frontend

React Router para as páginas listadas; layout público, autenticado e admin separados; componentes e hooks por feature. TanStack Query para `/api`; React Hook Form/Zod para cadastro, login, tópico, resposta e importação. Toda tela terá estados loading/error/empty, autorização refletida no UX e ainda aplicada no servidor. CSS atual pode ser migrado incrementalmente para CSS Modules/design tokens; preservar layout e acessibilidade onde existentes.

### Sessão e senha

Foi escolhida sessão opaca server-side em MySQL, sem alterar as tabelas PHP existentes. `node_sessions` guarda somente SHA-256 do token aleatório, usuário opcional, CSRF, flash message e expiração; o cookie é `httpOnly`, `SameSite=Strict`, `Secure` por padrão em produção, com TTL configurável (padrão de 1h). Login rotaciona o token, logout revoga a sessão e mantém o aviso de sessão seguinte. Mutations validam CSRF e `Origin`; a conta ativa e o papel são lidos no servidor. Redis e JWT não são usados.

Os endpoints `GET /api/auth/me`, `POST /api/auth/login`, `POST /api/auth/register` e `POST /api/auth/logout` agora consultam o schema de autenticação dedicado. Login aceita hashes compatíveis com `password_verify`; cadastro grava a tabela `usuarios` desse banco. A recuperação segue indisponível porque o PHP gera token descartável e não envia email nem persiste tokens.

Senha: suporte bcrypt no login Node para hashes compatíveis com PHP e estratégia sem reset obrigatório. Hashes PHP reais ainda precisam de um teste de paridade em cópia sanitizada. Não há rehash automático; coluna `senha` e hashes existentes não são alterados. No fluxo misto, sessões PHP/Node não compartilham estado: manter páginas PHP protegidas no runtime PHP até cutover coordenado; o cookie Node não autentica o PHP.

### Contratos compartilhados sugeridos

- `ExamType` é união explícita dos exames usados no simulador (TOEFL, IELTS, SAT, GRE, GMAT, DELE, DELF, TestDaF, JLPT, HSK); catálogo informativo é conceito à parte, não afirmar que todos têm questões cadastradas.
- Identificadores DB podem ser numéricos, mas schema real deve definir se API serializa como string para segurança de inteiro; não converter IDs indiscriminadamente.
- `ScoreDecimal` deve preservar o DECIMAL MySQL como string decimal (ou inteiro em centésimos) até renderização; não usar float JS para persistência/cálculo financeiro ou pontuação de paridade. Tempo é inteiro em segundos.
- Timestamp MySQL deve ser mapeado explicitamente para instante ISO-8601; preservar semântica atual `America/Sao_Paulo`/SQL e validar se DATETIME é local ou UTC antes de converter. `Date` JS e SQL podem divergir silenciosamente.
- Schemas Zod compartilhados devem representar exatamente as validações e coerções necessárias, mas entradas devem ser normalizadas explicitamente; nunca aceitar coercion implícita baseada no PHP.
- Valores e mensagens em português, redirects, status HTTP e JSON atuais de `salvar_resposta.php`/`processar_teste.php` precisam de fixtures de paridade. Mutação HTML antiga ganha UX SPA, mas não deve mudar regra nem mensagem sem decisão explícita.

## Variáveis de ambiente

O PHP atual não lê ambiente de forma detectada; valores de conexão/constants ficam em `config.php` (ignorado no Git). Nada de copiar credenciais a `.env` versionado. Proposta para o novo runtime:

| ------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------ |
| `NODE_ENV`                                        | modo de execução e defaults seguros            | Obrigatório                                                              |
| `API_PORT`                                        | porta Fastify                                  | Default `3001`                                                           |
